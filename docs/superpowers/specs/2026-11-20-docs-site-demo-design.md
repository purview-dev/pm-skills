# R-020 Docs-site package: rich demo — design

- Item: R-020 Docs-site package: rich demo planning fixture
- Brief: `planning/briefs/R-020-docs-site-demo-fixture.md`
- Branch: `feat/r-020-docs-site-demo-fixture`
- Date: 2026-11-20

## Intent

The user asked for "a demo site in repo, that shows all of the various features off". Today no place does that. `docs-site/` renders this repository's own plan, so it shows only the states that plan happens to be in. The package's test fixture is only reached through the tests. The demo is a checked-in site that anyone can open with one command to see every docs-site view filled with content. It is built the way a consumer builds one, so it also shows that the package works for a consumer.

The same item finishes five small tidy-ups left over from the R-018 re-review (user's choice: one pass).

## Goals

- `examples/demo/` is a consumer-shaped site that shows every view with content: board, roadmap with timeline, milestones and their pages, features and their pages, graph, Now, inbox, briefs, strategy, risks and their pages, log, and repository docs.
- Its plan is written as Markdown PM files and `pm-export` generates its `planning.json`, so the demo also shows the files a user writes.
- `just demo` opens it. `just demo-check` keeps it correct, and `just package-test` and CI run that check.
- The five tidy-ups are done.

## Non-goals

- Hosting or deploying the demo (`STRATEGY.md` `Not doing`: hosting the docs site).
- Replacing the package's test fixture (`packages/pm-docs-site/test/fixtures/planning.json`). Unit and browser tests keep it.
- New browser tests against the demo. The demo gets a build and content check only.
- Moving `docs-site/` onto the package (R-013).

## Anti-goals

- A demo that silently goes stale. If a schema, view, or skills-version change leaves it broken or out of date, `just demo-check` fails.
- Demo data that reads like this repository's real plan. It is clearly invented, so nobody mistakes it for pm-skills' own state.

## Constraints

- Every file is TypeScript where code is needed. No JavaScript, and no shell setting in the `justfile` (`sh` recipes only).
- The demo depends on the package by name, so it reads like a consumer site and becomes a version number once R-013 publishes the package.
- `bun install --frozen-lockfile` works in the demo, so `bun.lock` is committed.
- Package builds need Node 24 or later (`engines`).
- The demo's PM files follow the **PM file format** and lint clean with `pm-lint`.

## Approaches

| Approach | Trade-off | Outcome |
| --- | --- | --- |
| **A. Linked package plus a `demo-check` recipe** | Uses the local `packages/pm-docs-site` through a `file:` dependency with a frozen `bun.lock`. Linked sites already hydrate (R-017). The recipe must rebuild `dist/` first, or the demo shows the last build. | **Chosen** by the user. |
| B. Packed tarball, as in `install.test.ts` | Exactly what a consumer installs. The tarball hash changes every build, so no frozen `bun.lock`. It is slower and repeats `install.test.ts`. | Rejected. |

Data source, also decided with the user: Markdown PM files in `examples/demo/planning/`, with `planning.json` generated by `skills/pm-export/scripts/export.ts`. This was chosen over a hand-written `planning.json`, which would need hand edits on every schema change and nothing checking it against pm-export.

Location and check, decided in shaping: `examples/demo/`, opened with `just demo` and checked by `just package-test`.

## Design

### Layout

```text
examples/demo/
  package.json        # private; depends on "@purview-dev/pm-docs-site": "file:../../packages/pm-docs-site"; scripts as in "Package scripts"
  bun.lock
  astro.config.ts     # import pmDocsSite from '@purview-dev/pm-docs-site'; planning: 'planning/planning.json'; docs: the demo's docs/
  .gitignore          # dist/, .astro/, node_modules/
  README.md           # what the demo is, `just demo`, and that its plan is invented
  docs/               # 2 or 3 short Markdown pages for the repository-docs feature
  planning/           # a synthetic PM root, as pm-init lays it out
    config.md  VISION.md  STRATEGY.md  ROADMAP.md  NOW.md  LOG.md  RISKS.md
    inbox/  briefs/
    planning.json  planning.schema.json   # written by export.ts, never by hand
```

### The demo's plan

One invented product (builder's call; something neutral, such as a small booking or invoicing app). It must hold at least:

- 4 `V` lines, bets, assumptions, `Not doing`, and decisions in `STRATEGY.md` (fills the strategy page).
- 3 or more milestones with dates in `Target:`, one done, one the current focus, and one later; plus items with no milestone (fills the timeline, the milestone pages, and `milestones/none`).
- A full `Next` (up to the demo's max), a `Later` grouped by milestone, items of every owner (`agent`, `user`, `both`), size, and status (`ready`, `paused`, `blocked`). This fills every board column, including For you and Waiting.
- `Depends on` edges, including one item that depends on the active item. That draws an edge into the active node.
- A `Revisits` edge: an open item that revisits a done item.
- An active `NOW.md` item with `Done when` checks, a spec and plan path, and a checkpoint.
- `LOG.md` with Done lines across milestones, Dropped lines, and review entries.
- `RISKS.md` with open risks in red, amber, and green, one with a RAG override, one `mitigating` with a mitigation item, one `accepted`, a closed risk, and a removed risk.
- At least 3 inbox files (one bug with `## Reproduction`, one `Discuss: yes`) and 2 briefs (one on roadmap, one parked).

Dates sit relative to one fixed "today" (builder's call). The export records its own `generatedAt`, so the board window and Review due stay as generated.

### Generating the export

`bun skills/pm-export/scripts/export.ts write --root examples/demo --pm-root planning/` writes `planning.json` and `planning.schema.json`. `export.ts check` rebuilds the export as of its own recorded time and branch (`export.ts` lines 178 to 188), so the export stays `current` as the repository moves. It needs a re-run only when the demo's Markdown changes or the skills version moves, and that re-run is the fix `demo-check` prints.

### Staying current when the skills version moves

`planning.ts` writes the installed `skillsVersion` into `generator`, and `export.ts check` compares the whole document. So every rules major leaves the demo export out of date, including this item's own bump to 21. Designer's call: the bump does the re-run, so it is never a manual step.

- `scripts/bump-version.ts`, on a major or premajor bump, also writes the new major into `examples/demo/planning/config.md`'s `Rules version` and then runs `export.ts write --root examples/demo --pm-root planning/`. The demo's plan therefore always runs the rules the repository ships, and shows no upgrade debt.
- `demo-check` still fails when the export is stale, and prints the `export.ts write` command that fixes it. That covers a hand-edited demo file.
- Add one line to `AGENTS.md`'s build section: the demo export is derived and is refreshed by `just bump` or `export.ts write`.

### Package scripts

Designer's call: the demo's `package.json` scripts match the package README, the consumer's view: `"dev": "pm-docs-site dev"`, `"build": "pm-docs-site build"`, `"check": "pm-docs-site check"`, plus `"preview": "astro preview"`, because the CLI has no preview command. This means Node 24 is needed locally for `demo` and `demo-check`, as it already is for `package-test`. `astro` and `@astrojs/starlight` come in through the package's `dependencies`; the demo lists them directly only if `astro preview` or the config import cannot resolve them (builder checks).

### Recipes (`justfile`, `Docs` group)

- `demo`: build the package `dist/` (`node scripts/build.ts` in `packages/pm-docs-site`), then in `examples/demo` run `bun install --frozen-lockfile`, `bun run build`, `bun run preview` at <http://localhost:4321>. A built preview rather than `dev`, because search works only on a build.
- `demo-check`, in this order:
  1. `bun skills/pm-export/scripts/export.ts check --root examples/demo --pm-root planning/`
  2. `bun skills/pm-export/scripts/export.ts validate examples/demo/planning/planning.json`
  3. `bun skills/pm-lint/scripts/lint.ts check --root examples/demo --pm-root planning/`
  4. Build the package `dist/`, then `bun install --frozen-lockfile` and `bun run build` in `examples/demo`.
  5. `bun scripts/check-demo.ts`
- `package-test` runs `demo-check` after its own steps, and `.github/workflows/ci.yml`'s package job gets the same commands as steps.

### `scripts/check-demo.ts`

A dependency-free Bun script (with a test in `scripts/`) that reads `examples/demo/dist/`:

- The built HTML page list equals `examples/demo/expected-pages.txt`, so a view or page that stops being built fails.
- No page under `plan/` contains an element with class `plan-empty`, the class every view uses for its empty state (`now.astro`, `inbox.astro`, `strategy.astro`, `risks.astro`, `graph.astro`, `roadmap.astro`, `milestones/`, `briefs.astro`, `FeatureTable.astro`). A short allowlist in the script holds the `plan-empty` uses that are not empty states (the risk matrix's `–` cells and legend in `risks.astro`), and "Nothing links here yet." (`LinkedFrom.astro`) on feature pages that no item links to. Each allowlist entry has its reason.
- On failure, it prints the page and the empty-state text.

### Tidy-ups (from the R-018 re-review)

1. `packages/pm-docs-site/src/routes/plan/now.astro` reads the active item's owner and size from `now.item`, not `board.columns.now[0]` (line 16), so the page has one source, as `features()` does.
2. `skills/pm-board/SKILL.md`'s Now card step says the card's owner and size come from `NOW.md`.
3. Remove the unreferenced `$defs/itemRef` from `skills/pm-export/references/planning.schema.json`. `schemaVersion` stays 4, because the document shape does not change. Every consumer's `export.ts check` then reports that the schema differs until it re-exports; the rules 21 upgrade already tells consumers to run `pm-setup`, and the upgrade note asks them to run `pm-export` once. Copy the schema to `planning/planning.schema.json` with `export.ts write`, and keep the example and validator passing.
4. `packages/pm-docs-site/test/graph.test.ts` (lines 76, 116, 140, 158) builds each partial `Planning` by spreading the fixture instead of `as unknown as Planning`.
5. The package fixture `packages/pm-docs-site/test/fixtures/planning.json` gains an item whose `Depends on` names the active item (R-012), so the shared fixture draws an edge into the active node. Update `expected-pages.txt` and any test that counts edges.

### Versioning

Tidy-ups 2 and 3 change `skills/**`, and `v20.0.0` is tagged, so the item raises the rules to 21: `just bump premajor` (`21.0.0-pre.1`), then `pm-setup` to install the rules here. Add a `Version 21` upgrade note to the managed section (`skills/pm-setup/references/AGENTS-section.md`) saying to run `pm-export` once, because the export schema file changed while `schemaVersion` stayed 4.
